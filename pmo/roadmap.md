# Roadmap

## Now

The Now horizon completes governed Discovery. It uses broad online statistics to rank workflow scope across varied project types, keeps historical authenticated reference material quarantined, compares open-source alternatives, proves a feasible technical direction, defines first-release scope, writes requirements and outcome contracts, and records all work in project-local Control Tower.

Now also establishes the clean-room policy: independent code and assets, synthetic fixtures, private evidence isolation, distinct branding, and repeatable public provenance checks. Discovery records a validated package and any warning with an owner and handoff rationale.

## Next

The Next horizon is Sprint Planning and the first vertical implementation slices. Planning produces the PRD, architecture, data model, API contracts, UX flows, design tokens, accessibility approach, threat model, migration strategy, test matrix, acceptance criteria, and issue graph. It chooses the framework and license only after documenting tradeoffs and authority.

Implementation begins by migrating application persistence to embedded SQLite, collapsing the release into one loopback Node process, preserving internal scope metadata, and establishing the design-system shell, seeded fixtures, and deterministic visual harness. The next slices deliver project/milestone planning, issue execution, views/search, activity/relations, and backup/restore as end-to-end capabilities. Visual refinement follows functional vertical closure rather than preceding it.

## Later

Later begins after independent Testing and release-candidate acceptance. The [Feature Log](./feature-log.md) orders candidates and records their Control Tower mappings. Candidate features include templates, project updates, richer progress analytics, generic imports, timelines, calendars, desktop packaging, mobile refinement, and local automation. Remote access, real-time presence, webhooks, multiple users, and OIDC require new Discovery because they change the accepted security and concurrency boundary. Cycles and initiatives enter research only if new broad evidence shows that they materially block migration.

AI agent features, code review, customer management, billing, and marketplace integrations remain beyond the first product lifecycle. They need separate Discovery because they change data, permission, and product boundaries.

## Dependencies

Discovery depends on private Chrome research remaining read-only and Control Tower local authority remaining healthy. Planning depends on accepted outcomes and benchmark tasks. Implementation depends on selected architecture, synthetic fixture schema, public identity working boundary, and security model. Testing depends on a sealed candidate revision, reproducible environment, migration fixtures, and visual baselines. Public release depends on the technical audit, dependency attribution, restore evidence, and a complete source distribution.

No Google account, Linear service, Docker runtime, database server, OIDC configuration, or paid service is a v0.1 runtime dependency.

## Exit criteria

Now records five Discovery outputs, exact critical QA, validated normalized JSON, private source preservation, and fresh Control Tower issue/milestone readback. Next records evidence that the release can complete every core workflow on synthetic data, local-origin and filesystem security tests pass, the visual harness is stable, and SQLite backup/restore succeeds. Testing records independent evidence for every Must requirement and critical finding. Release is ready when the current technical audit and secret scan pass.

Dates are targets, not proof. A milestone remains incomplete until its evidence is present. Progress derives from issue state and current verification results.

## Re-planning triggers

Re-plan when new credible population evidence overturns CT-77's stable top-three workflow set, product measurements show the interaction target is unattainable, the accepted workload cannot meet the one-process SQLite boundary, local-origin or filesystem protection cannot be enforced without redesign, licensing prevents the intended distribution, clean-room review requires a materially different visual direction, or more than twenty percent of Must requirements change after implementation starts.

Re-plan rather than silently add scope when cycles, initiatives, native apps, or integrations become migration blockers. A local defect does not justify full roadmap reset; the owner shows which dependencies and outcomes actually change.
