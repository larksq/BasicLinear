# Assumptions and Open Questions

## Assumptions

| ID | Assumption | Why it matters | Current treatment |
|---|---|---|---|
| A-001 | One technically capable owner can be the complete supported v0.1 decision unit. | Segment choice controls onboarding, permissions, scale, and acceptance. | Accepted by sponsor instruction and bounded by CT-77's broad statistical workflow ranking; reassess only through a later multi-user Discovery. |
| A-002 | Projects, milestones, issues, views, search, relations, activity, and recovery capture enough reference value for a first release. | Missing a migration-critical object could invalidate scope. | CT-77 ranks these workflow families; controlled product measurements still test their implementation. |
| A-003 | One loopback Node 24 process plus an embedded SQLite file is acceptable to personal-use owners. | Installation burden can erase the ownership value proposition. | Accepted as the CT-79 direction; CT-82 must independently measure clean local start, upgrade, backup, restore, and rollback. |
| A-004 | A TypeScript web client/service can meet reference interaction latency on commodity hardware. | The architecture and component strategy depend on it. | Prove with an early seeded performance slice. |
| A-005 | A distinct visual identity can retain spatial and interaction fidelity. | Clean-room safety and differentiation both depend on separation from brand identity. | Validate with side-by-side workflow review and qualified release review. |
| A-006 | The sponsor selected `AGPL-3.0-only` for the repository. | License affects hosted modifications, adoption, contributors, and dependencies. | Repository metadata is updated; qualified compatibility, notice, and contribution review remain open under CT-3/CT-13. |

## Open questions

What task-time and interaction-count baseline should define “near-reference”? Which public name avoids confusion while communicating the product category? What evidence would justify a later multi-user, remote, or multi-team release? Which rich-text format best preserves portability? What seeded scale should govern latency budgets beyond CT-79's personal-use ceiling? Which import formats materially lower switching cost?

These questions are not interchangeable. CT-77 resolves workflow order for v0.1 while deployment and product measurements affect acceptance. Public name and license block publication. Multi-user, multi-team, real-time, editor, and import decisions require their own later evidence and architecture review. Each receives one validation path and decision point.

## Validation plan

V-001 was superseded before outreach. CT-77 instead synthesizes four official large-sample sources with explicit denominators, represented populations, limitations, vendor conflicts, weighted ranking, and sensitivity analysis. It seals the v0.1 workflow order without claiming migration rate, usability, or exact switching effort.

V-002 defined and ran eight reference tasks as an automated internal diagnostic without Linear API, MCP, or task-tracking writes. CT-3 now quarantines those aggregates from publication and pauses further authenticated measurement pending qualified review. Eligible-user evidence and the accepted observation window are still required before any efficiency outcome decision.

V-003 compares AGPL-3.0, MPL-2.0, Apache-2.0, and relevant dependency licenses, then records a sponsor decision. A qualified reviewer completes public identity and clean-room review before release branding or distribution.

V-004 builds three technical spikes: workspace-scoped CRUD with revision conflicts, dense issue list with keyboard details, and deterministic visual snapshots. The technical lead completes them before architecture acceptance.

V-005 is replaced by CT-82. It rehearses one-command local start, loopback security, upgrade, SQLite online backup, verification, restore, rollback, canonical PostgreSQL-export import, and outbound-denied runtime on a clean supported user account without Docker or a database server.

## Owners

The discovery owner owns CT-77 evidence registration and future population refreshes. The UX owner owns V-002 and clean-room flow specifications. The product owner owns the one-owner scope, name, and license decisions. A qualified legal or brand reviewer supports V-003. The technical lead and security owner own V-004. The operations and test owners jointly own V-005. Control Tower local issues carry these deliverables, due dates, status, and milestone.

Ownership by function is governance metadata, not product membership UX. The single product owner performs the supported workflow while independent reviewers retain security, accessibility, legal, test, and release authority. A delayed decision records its impact and revised review date rather than disappearing.

## Decision dates

CT-77 completed the v0.1 workflow decision on 2026-08-21. CT-79 replaced the Docker/PostgreSQL hypothesis with the local SQLite direction on the same date. V-002's accepted efficiency evidence remains pending despite the completed internal diagnostic. The sponsor license decision is recorded as `AGPL-3.0-only`; public-name, qualified license, and clean-room clearance remain mandatory before any public release candidate. CT-82 occurs before Testing accepts operational readiness.

If dates slip, private implementation may continue only where the missing answer cannot create expensive divergence. Public branding, license publication, and final UX thresholds do not proceed on assumption alone.
