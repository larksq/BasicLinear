# Assumptions and Open Questions

## Assumptions

| ID | Assumption | Why it matters | Current treatment |
|---|---|---|---|
| A-001 | One technically capable owner can be the complete supported v0.1 decision unit. | Segment choice controls onboarding, permissions, scale, and acceptance. | Accepted by maintainer instruction and bounded by CT-77's broad statistical workflow ranking; reassess only through a later multi-user Discovery. |
| A-002 | Projects, milestones, issues, views, search, relations, activity, and recovery capture enough reference value for a first release. | Missing a migration-critical object could invalidate scope. | CT-77 ranks these workflow families; controlled product measurements still test their implementation. |
| A-003 | One loopback Node 24 process plus an embedded SQLite file is acceptable to personal-use owners. | Installation burden can erase the ownership value proposition. | Accepted as the CT-79 direction; CT-82 must independently measure clean local start, upgrade, backup, restore, and rollback. |
| A-004 | A TypeScript web client/service can meet reference interaction latency on commodity hardware. | The architecture and component strategy depend on it. | Prove with an early seeded performance slice. |
| A-005 | A distinct visual identity can retain spatial and interaction fidelity. | Clean-room safety and differentiation both depend on separation from brand identity. | Validate with independent workflow checks and technical asset/copy provenance. |
| A-006 | The maintainer selected `AGPL-3.0-only` for the repository. | License affects hosted modifications, adoption, contributors, and dependencies. | Repository metadata, notices, contribution policy, and the technical release audit are current. |

## Open questions

What task-time and interaction-count baseline should define “near-reference”? Which public name avoids confusion while communicating the product category? What evidence would justify a later multi-user, remote, or multi-team release? Which rich-text format best preserves portability? What seeded scale should govern latency budgets beyond CT-79's personal-use ceiling? Which import formats materially lower switching cost?

These questions are not interchangeable. CT-77 resolves workflow order for v0.1 while deployment and product measurements affect acceptance. The public name and license are recorded inputs checked by the technical release audit. Multi-user, multi-team, real-time, editor, and import decisions require their own later evidence and architecture review. Each receives one validation path and decision point.

## Validation plan

V-001 was superseded before outreach. CT-77 instead synthesizes four official large-sample sources with explicit denominators, represented populations, limitations, vendor conflicts, weighted ranking, and sensitivity analysis. It seals the v0.1 workflow order without claiming migration rate, usability, or exact switching effort.

V-002 defined and ran eight reference tasks as an automated internal diagnostic without Linear API, MCP, or task-tracking writes. CT-3 quarantines those aggregates from publication and prohibits further authenticated measurement. Eligible-user evidence and the accepted observation window are still required before any efficiency outcome decision.

V-003 compares AGPL-3.0, MPL-2.0, Apache-2.0, and relevant dependency licenses, then records a maintainer decision. The technical release audit verifies public identity anchors, notices, provenance, and clean-room publication controls.

V-004 builds three technical spikes: workspace-scoped CRUD with revision conflicts, dense issue list with keyboard details, and deterministic visual snapshots. The technical lead completes them before architecture acceptance.

V-005 is replaced by CT-82. It rehearses one-command local start, loopback security, upgrade, SQLite online backup, verification, restore, rollback, canonical PostgreSQL-export import, and outbound-denied runtime on a clean supported user account without Docker or a database server.

## Owners

The maintainer owns CT-77 evidence registration, clean-room flow specifications, the one-owner scope, public identity, license, and release evidence. Technical, security, operations, and test work define V-003 through V-005. Control Tower local issues carry these deliverables, due dates, status, and milestone.

Ownership by function is governance metadata, not product membership UX. The single maintainer performs the supported workflow and relies on repeatable security, accessibility, test, and release checks rather than external approval gates. A delayed decision records its impact and revised date rather than disappearing.

## Decision dates

CT-77 completed the v0.1 workflow decision on 2026-08-21. CT-79 replaced the Docker/PostgreSQL hypothesis with the local SQLite direction on the same date. V-002's accepted efficiency evidence remains pending despite the completed internal diagnostic. The maintainer license decision is recorded as `AGPL-3.0-only`, and the BasicLinear identity, notices, provenance, and clean-room controls are checked by the technical release audit. CT-82 provides operational-readiness evidence.

If dates slip, private implementation may continue only where the missing answer cannot create expensive divergence. Public branding, license publication, and final UX thresholds require current technical evidence rather than assumption.
