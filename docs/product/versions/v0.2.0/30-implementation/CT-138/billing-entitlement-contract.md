# CT-138 trial, subscription, seat, and Free fallback contract

## Accepted product boundary

CT-138 implements I-206 only. Every new hosted owner receives exactly one immutable Pro trial lasting 30 consecutive 24-hour periods. Creating another workspace, retrying bootstrap, signing in again, changing a clock presentation, or changing a Google email cannot restart it. No card is requested during bootstrap and no charge begins automatically.

The two supported subscription choices are USD $2 per active hosted user per month and USD $12 per active hosted user per year, before tax. The owner sees the absolute monthly and annual totals before choosing. Applicable tax is calculated automatically in the payment provider's hosted Checkout, and BasicLinear validates that automatic tax remains enabled on every current-subscription read and quantity update. The owner must make an explicit plan choice and then confirm on the provider page. Pending invitations are displayed separately and never counted as seats; every active membership, including the owner, is one seat.

This slice deliberately excludes coupons, trials controlled by the payment provider, metered billing, usage pricing, custom enterprise contracts, multiple currencies, refund initiation inside BasicLinear, invoices managed inside BasicLinear, tax advice, production activation, REST tokens, export implementation, MCP, AI agents, code review, repositories, and pull requests. Checkout enables provider-calculated automatic tax; BasicLinear totals are the exact USD price before applicable tax. A refund event alone never changes access: current subscription status and paid-through state remain authoritative until a signed subscription notice is reconciled.

## Trusted price and provider boundary

Prices, currency, recurrence, price identifiers, seat quantity, workspace/customer/subscription binding, success/cancel destinations, and proration behavior are trusted-service inputs. Browser requests contain only the supported plan key and a bounded idempotency key. Any client-supplied price, amount, currency, quantity, customer, subscription, trial, return URL, or metadata field is rejected rather than ignored.

Checkout creation uses subscription mode, one server-selected recurring price, and the active-seat count recomputed from trusted membership records. Adjustable quantity is not enabled. If membership state changes across provider creation, the trusted service expires the newly created session and returns a retryable conflict rather than presenting a stale total.

One authenticated singleton Checkout lock exists per workspace. Concurrent tabs and distinct idempotency keys cannot open a second provider session, including a second plan, while one session is being prepared, remains open, or has completed and awaits a signed notice. Every Checkout attempt carries an opaque HMAC-derived Checkout reference in exact provider metadata, and the signed local record binds the attempt number, attempt time, provider creation time, session, customer, and eventual subscription. If provider creation succeeds but both normal persistence and the first fallback persistence fail, a same-key retry recovers the provider's idempotent open, expired, or completed session and durably binds it even when membership changed after provider completion. Once the provider's idempotency-retention window may have elapsed, the service first performs a time-bounded paginated enumeration of every provider Checkout page, without an arbitrary global-record ceiling, and retains only sessions carrying that exact opaque reference. Empty or repeated provider cursors fail closed; enumeration must finish before any attempt advances. The service expires any recovered open session, refuses ambiguous multiple completions, and binds a single completion. Only after it has established that every prior attempt is expired or absent may it advance the authenticated attempt and issue another provider request from current seat state. A failed seat-drift finalization therefore cannot leave either a chargeable orphan or a permanent unbound lock.

Provider creation chronology is identical on every write path. Both normal binding and cleanup/fallback persistence compare the provider-created timestamp with trusted current time using the same five-minute tolerance before treating it as canonical. A farther-future open or expired session can be expired but cannot become a locally bound `ready` record; the valid authenticated `prepared` attempt remains readable and can rearm after the bounded recovery interval. A single exact completed session is different because blindly rearming could create a second subscription. For that state only, the Checkout stores the trusted attempt time and bounded logical expiry as its canonical chronology plus a tamper-evident digest explicitly labeled as untrusted provider chronology. It binds the exact session without granting access. The verified signed notice must then retrieve and bind the exact current provider subscription, workspace, owner, customer, plan, price, and Checkout quantity before entitlement converges and the Checkout is sealed completed. If the initial local bind failed, notice preflight synthesizes and validates the exact recovered binding without writing it; the final transaction repeats those checks and atomically creates the session binding, completes the Checkout, persists billing and webhook records, and emits activation evidence. A failure between preflight and final persistence therefore leaves the authenticated Checkout `prepared` with no binding or paid ledger; duplicate notices replay the same completion, and no retry opens another provider session.

Before opening any replacement Checkout, the service retrieves the currently bound provider subscription. Replacement is allowed only after a coherent terminal `canceled` or `incomplete_expired` state is recorded. Every recoverable or nonterminal state—including `active`, `past_due`, `unpaid`, `incomplete`, `paused`, and `trialing`—blocks replacement, even when it grants only Free access, so an older subscription cannot later recover beside a replacement and charge the same workspace twice.

Webhook signatures are verified from the unparsed bounded request body with the provider SDK's nonzero timestamp tolerance. Event identifiers are deduplicated, but event order and event payload subscription state are not trusted. Each valid notice causes a fresh retrieval of the current provider subscription. Workspace, customer, subscription, price, interval, metadata, and automatic-tax-enabled bindings must all match before any entitlement change. The completed Checkout's plan and price remain strict activation evidence on first use; after that Checkout is durably completed, the same subscription/customer identity may converge to a different supported current plan and price without rewriting its historical Checkout evidence. Duplicate and out-of-order notices therefore converge on the current provider state.

Active-seat changes use an explicit proration policy. The service updates only an `active` provider subscription quantity from trusted membership state and never accepts a browser-provided quantity. Every adapter call carries the exact expected subscription, customer, workspace, owner, plan, price, current quantity, active status, paid-through boundary, and cancellation state from the service preflight. The Stripe adapter validates that relative binding on its immediate current-subscription read before making any quantity mutation, validates the returned subscription again after mutation, and explicitly preserves automatic tax; the service independently repeats the post-update identity check before any billing-ledger write. A structurally valid between-read change therefore produces zero quantity update, and a divergent update result cannot be persisted against another workspace. Inactive lifecycle notices are recorded authoritatively without attempting proration, so a canceled or failed-payment provider state cannot leave the local ledger stale-active merely because quantity update is unavailable. Each provider quantity-update idempotency reference is authenticated over the workspace, exact subscription ID, billing revision, and membership fingerprint: identical retries are stable, while a later subscription or recurring membership set cannot collide with an earlier provider operation. A just-accepted or just-removed seat pauses paid writes until live membership count and the authenticated billing ledger agree; the exact mutation retry invokes reconciliation again without adding or removing another seat. Provider secrets, webhook bodies, signatures, checkout secrets, card/payment data, raw provider event identifiers, and raw idempotency keys are excluded from product events, mutation audits, logs, errors, and browser-readable records.

## Entitlement state and downgrade behavior

The bootstrap trial document remains immutable and is never extended with billing fields. A separate trusted billing record records only provider references, selected plan, current provider lifecycle, paid-through boundary, reconciled seat quantity, and authenticated lifecycle metadata.

The effective state is evaluated from trusted time and records:

- `trial_pro` while the original trial end is strictly in the future and no valid paid subscription supersedes it;
- `paid_pro` only while a correctly bound current subscription is `active` and its paid-through boundary is strictly in the future; paid mutations additionally require its reconciled provider quantity to equal the live active-membership count;
- `free` otherwise, including `past_due`, `unpaid`, `incomplete`, `incomplete_expired`, `paused`, `trialing`, canceled, expired, malformed, unavailable, or unbound billing state after trial expiry.

Downgrade never deletes tasks, comments, memberships, invitations, or workspace records. Free keeps all workspace data readable and eligible for the future CT-139 export path; CT-138 does not expose or claim an available export operation. One writer remains: the active owner through a verified user session (web now; future REST/MCP user-session forms), never a personal token or automation principal. Other members, personal tokens, automation, invitations that add seats, assignment to another user, and multi-user writes pause until the owner subscribes or reduces the workspace. Existing invitations remain visible and revocable so recovery is possible. The owner can remove an active non-owner member through a confirmed, idempotent control; the membership becomes `removed`, access ends, task/comment records remain, a privacy-safe audit is authenticated on replay, and any active paid quantity is reduced with the same explicit-proration path.

Entitlement is checked again inside every affected mutation transaction after authorization and membership validation. A prior authorization result, browser summary, or cached plan cannot permit a write after expiry or payment loss. Unavailable, malformed, cross-workspace, time-inconsistent, or unauthenticated entitlement records fail closed without mutating protected state.

Scheduled cancellation remains paid only through the trusted period boundary. A stale `active` record at that boundary cannot create another subscription until a fresh provider read confirms a coherent terminal or renewed state. Failed-payment states fall back as listed above. Refund/charge events are signature-checked but ignored for entitlement; only a freshly retrieved subscription lifecycle can change access. Automatic tax is provider-calculated, while BasicLinear continues to show the accepted pre-tax USD total.

## Evidence and claims

The existing CT-133 immutable `trial.started`, `trial.ended`, and `subscription.activated` event contracts are reused. Trial end emits once at the original boundary; subscription activation emits only for an actual transition to a valid paid state. Events contain no payment secrets or customer-facing financial data beyond bounded plan/seat outcome fields already accepted by the measurement contract.

O-201 and O-203 remain `baseline_needed`. This implementation and its sandbox provider tests do not activate a live Stripe account, accept provider terms, create production price objects, process money, deploy a service, qualify P-T206, approve release, or establish legal, privacy, security, or financial approval.
