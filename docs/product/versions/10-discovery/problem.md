# Problem

## Recommendation

Build an independent, self-hostable project-management core for one technically capable owner using one automatically provisioned workspace and team. Match the reference product's workflow speed and spatial discipline on approved project, issue, milestone, view, search, and detail fixtures. Do not attempt broad parity with collaboration administration, cycles, initiatives, AI, code review, analytics, or integrations in `v0.1.0`.

## Target user and role

The supported v0.1 user is one technically capable owner who defines projects and milestones, captures and reviews issues, and operates backup and restore. One owner profile plus internal workspace/team identifiers are automatically provisioned in the local SQLite file. Membership, multi-user accounts, invitations, role administration, team/workspace switching, sharing, and non-owner assignment are outside the supported runtime and UX. CT-77's broad statistics support the workflow order, not a claim that every represented respondent is a prospective user.

## Current workflow

The observed reference workflow uses a persistent navigation rail, dense list and board views, keyboard creation, inline metadata, details that preserve context, document-like project overviews, lightweight milestones, and visible activity. An owner who requires open source or self-hosting must either accept a proprietary service, adopt a broader open-source alternative with a different interaction model, or assemble repository and task tools.

## Alternative insufficiency

Plane, OpenProject, Taiga, Vikunja, and GitHub Projects cover meaningful parts of the category. Their existence invalidates “open source” as sufficient differentiation. The opportunity is the combined outcome: reference-grade interaction quality, narrower operational complexity, complete data portability, and an independently designed clean-room implementation. CT-77 ranks the necessary workflow families; it does not claim preference, adoption, or migration rate.

## Replacement boundary

`v0.1.0` is a replacement for the defined core, not orchestration around Linear. It has no Linear runtime, API, MCP, or synchronization dependency. It does not copy code, assets, trademarks, proprietary fonts, hidden endpoints, or private content. The sponsor requested “OpenLinear” as the final product brand and “Scopefold” as the project identity, but that model remains blocked from public use until `CT-3` resolves current collision evidence and qualified clearance.

## Trust conditions

Users must be able to run one loopback process without Docker, a database server, login, or a paid service; export and restore authoritative data; understand conflicts and destructive actions; operate keyboard-only; protect local data from hostile browser origins and unsafe paths; inspect activity; and upgrade with rollback evidence. Private research evidence cannot enter the distribution.

## Observable behavior change

The configured owner moves from dependence on a proprietary tracker or a slower substitute to a self-hosted system where at least nine of ten canonical seeded workflow runs complete successfully, with near-reference interaction efficiency, accepted structural visual fidelity, and complete data round trips.

## Invalidation

The product direction is invalidated if credible population evidence overturns CT-77's stable top-three workflow set, core workflow completion remains at or below 70 percent after two bounded remediation rounds, local data is exposed through a remote listener, hostile origin, or unsafe path, backup/restore loses authoritative records, clean-room review fails, or credible comparative evidence consistently favors an existing open-source alternative.

## Downstream handoff

Planning receives the first-release boundary, R-001 through R-110, O-001 through O-005, source and evidence indexes, clean-room constraints, CT-77's workflow ranking, and the CT-2 through CT-4 results. It may not reintroduce multi-user UX or invent missing license, brand, benchmark, migration, or usability conclusions.
